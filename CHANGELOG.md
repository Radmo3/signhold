# Changelog

## Unreleased

- **On-chain enforcement for Safe wallets: `SignholdGuard`** (`contracts/safe-guard`, `@signhold/safe-guard`, Apache-2.0, unaudited). A Safe transaction guard (Safe 1.4.1 / 1.5.0 `ITransactionGuard`) that lets the Safe execute a transaction only with an unexpired EIP-712 attestation of the service's verdict for that exact Safe transaction hash (`block` is never attested) and, for `escalate` and for anything touching the Safe's configuration, the guard, a delegatecall or a gas refund, a single-use EIP-712 approval signed by a registered device (secp256k1, or P-256 through the RIP-7212 / EIP-7951 precompile, fail-closed where the precompile is absent). Attestations may only tighten, never loosen; the attestor can never be an approver; owners keep an escape hatch (`setGuard(address(0))` approved by a device, with or without the service). Hardhat 3 + viem tests against a real Safe 1.5.0 (27 cases, gas report, native and mocked precompile), Slither clean, TypeScript helpers (Safe tx hashing, typed data, `createAttestor`, viem submit helpers, a trusted-display device flow and `approve-safe.ts` CLI). This mitigates the "agent-side bypass" and "service verifies approvals" residuals for Safe wallets; they remain for non-Safe signers (docs/THREAT_MODEL.md).
- **API**: `SIGNHOLD_ATTESTOR_KEY` / `ServerOptions.attestor` and `POST /v1/attestations` (signs a verdict only for the exact audited intent as a plain call; `block` → 403; `attestation` / `attestation_refused` audit records, checked by `verify-audit.ts`); `SIGNHOLD_APPROVER_KEYS` accepts secp256k1 addresses (`id:0x…` / `id:secp256k1:0x…`); `POST /v1/approvals` accepts `scheme: "eip712"` approvals bound to the issued attestation, so one device signature works off-chain and on-chain. SDK: `client.requestAttestation()`. `examples/safe-guard-demo.ts` (`npm run demo:safe-guard`).

- **Coinbase AgentKit integration** (`integrations/agentkit`, `@signhold/agentkit`): `guardWalletProvider()` wraps an AgentKit `EvmWalletProvider` so `sendTransaction` / `signTransaction` / `nativeTransfer` (and the account returned by `toSigner()`) go through `POST /v1/check` first, with raw-hash / typed-data / message signing and every provider escape hatch (`getClient()`, `exportWallet()`, `smartAccount`, `ownerAccount`, legacy CDP `gaslessERC20Transfer` / `createTrade` / `deploy*`, ZeroDev `getKernelAccount` / `getIntentClient`) refused by default; `signholdActionProvider()` exposes two read-only actions (`signhold_check_status`, `signhold_explain_last_decision`) and no approval surface. Built against `@coinbase/agentkit@0.10.4` type definitions (compile-time probe), exercised only with a mock provider. `examples/agentkit-demo.ts` (`npm run demo:agentkit`).
- **SDK `guard()` hooks** for the above: `methods` (which methods to check, with per-method intent mappers), `deny` (members refused with the new `GuardUncheckableError`), `bindPassthrough` (pass-through methods run with the real instance as `this`, required for classes with `#private` fields) and `reentrant` (factories such as `toSigner()` see the proxy as `this`). Defaults unchanged. `EscalationInfo.method` is now `string`.
- **Cap-bypass experiment**: `--framework reference|agentkit` runs the scenarios through AgentKit-shaped actions and `guardWalletProvider()` around an `EvmWalletProvider`-shaped wallet over the ledger; results and summaries carry `framework`, the report groups by it when more than one is present, and the smoke run covers both. The wallet's e-mail clock is now deterministic (the OTP mail's timestamp no longer depends on wall-clock time).

## 0.2.0 (21 Nov 2026)

- **Inalienable human approval of escalations (I-HITL).** An `escalate` verdict now stays blocked on the server until `POST /v1/approvals` receives an Ed25519 signature from a key registered in `SIGNHOLD_APPROVER_KEYS` over a challenge sealed into the signed audit record (bound to audit id, intent hash, decision hash, policy, agent id, issue time). Single use, 15-minute TTL, any invalid attempt burns the challenge, approvals and rejections are chained audit records. The SDK can only poll `GET /v1/approvals/:auditId`; `guard()` defaults to `approval: "server"` and refuses an in-process `onEscalate` callback in that mode (the old behaviour survives only as opt-in advisory mode with a startup warning). Addresses a review by one of the I-HITL authors (arXiv:2610.35835). Weak I-HITL in that paper's terms: enrollment is unattested.
- **Trusted-display approver CLI.** `approve.ts` fetches the sealed audit record itself, recomputes the challenge, shows the decoded transaction, requires a typed confirmation, and never signs a bare challenge.
- **Threat model T7** ("agent reaches the approval channel") and three adversarial tests for forged, replayed and re-bound approvals.
- **Technical report** in `docs/report/` (15 pages) with evaluation logs.
- **Cap-bypass experiment harness** (`experiments/cap-bypass/`, private workspace, not published): a simulated reproduction of the I-HITL cap-bypass study (arXiv:2610.35835) with a `baseline` arm and a `signhold` arm (in-process API, operator-held policy, approver-device fixture unreachable from the agent), scripted agents for CI (`npm run experiment:smoke`), Anthropic / OpenAI / OpenAI-compatible model adapters, JSONL results with Wilson intervals and a markdown report. No network, no funds.
- **Renamed the project from AgentGuard to Signhold.** Signhold was briefly published as AgentGuard (Nov 2026) and renamed to avoid a conflict with an unrelated registered trademark. Package scope `@agentguard/*` is now `@signhold/*`, environment variables `AGENTGUARD_*` are now `SIGNHOLD_*`, the request-signing headers `x-agentguard-{signature,timestamp,nonce}` are now `x-signhold-{signature,timestamp,nonce}`, and the SDK classes `AgentGuard*` are now `Signhold*`. No security behaviour, canonical signing string, audit record format or policy semantics changed. Nothing had been published to npm under the old names.
